# 商品列表加载优化

## 诊断

在真实 1480 商品工作区，只读访问 Go 列表接口：首次 57ms，后续 18–21ms；50 条列表原始响应约 149KB。服务器本地 Next 无登录请求 4–38ms，Windows 经 SSH 转发的小响应约 68–91ms；同一通道约 250KB 的脚本下载一次约 1.9 秒。后两项仅用于网络与代理基线，不冒充真实登录会话的完整链路计时。

因此不将用户观察到的 1 秒多归因于 1000 多条数据的数据库查询；传输、请求排队及浏览器开销仍需根据具体请求区分。

## 改动

- 列表去掉已由公开别名提供的重复机器字段及只需详情展示的 evidence；商品详情仍返回完整数据。
- Next 对商品/父子商品列表 JSON 按 Accept-Encoding 协商 gzip，使用流式压缩，保留 no-store。下载文件和写入响应不受此压缩路径影响；禁止认证结果共享缓存。
- 响应 Server-Timing 提供 auth、api、proxy 毫秒计时。proxy 表示直到准备响应头的服务器耗时，不包含最终下载和浏览器渲染；浏览器仍以 Network Timing 为准。
- 已有 React Query 60 秒缓存继续使用。切换页码/筛选时保留同租户上次结果，显示更新提示；暂时禁用旧行操作，防止把旧内容误当成新结果操作。
- 列表完成后延迟低优先级预取下一页；修改筛选时取消过期的读取请求。预取复用相同租户缓存键，变更操作仍按原规则失效缓存。
- 采用指南 js 的请求取消及 deprioritize-background-fetches 的低优先级预取：priority 为渐进增强，不支持的浏览器仍可正常请求。

## 验证

检查压缩协商（包含 gzip q=0 与 wildcard）、Server-Timing、类型、相关 lint 和生产构建；隔离 Chrome 检查列表 Content-Encoding/Server-Timing 与 JSON 解码，同时回归既有初筛流程。业务查询变更使用独立 PostgreSQL 测试数据；不修改真实商品或人工结论。
